# printerctl Architecture

## 1. Purpose

`printerctl` is a Linux command-line application written in C17 that controls 3D printers running Marlin Firmware over USB serial.

The MVP focuses on reliable, observable and fault-tolerant G-code transmission from files generated by PrusaSlicer. The system must be safe by default, testable without real printer motion and modular enough for autonomous development by Codex-orchestrated agents.

## 2. Architectural Principles

1. **Safety first**: never home, heat, move axes or extrude unless explicitly requested by the operator.
2. **Acknowledgement-driven streaming**: send one command and wait for Marlin acknowledgement before sending the next command.
3. **Observable operation**: log commands, responses, progress, errors and state transitions.
4. **Modular C design**: isolated modules with explicit interfaces and no avoidable global mutable state.
5. **Testability without hardware**: core behavior must be validated through pseudo terminals, mocks and dry-run mode.
6. **Portable Linux implementation**: support GCC and Clang with CMake and warning-free builds.
7. **Future compatibility**: leave extension points for Marlin line numbers, checksums and resend handling.

## 6. Module Responsibilities

### 6.1 `cli`

Parses command-line arguments, validates user intent and dispatches commands.

Expected commands:

```bash
printerctl --port /dev/ttyACM0 print file.gcode
printerctl --port /dev/ttyACM0 pause
printerctl --port /dev/ttyACM0 resume
printerctl --port /dev/ttyACM0 cancel
printerctl --port /dev/ttyACM0 temp
printerctl --port /dev/ttyACM0 position
printerctl --port /dev/ttyACM0 info
printerctl --port /dev/ttyACM0 send "M115"
printerctl --dry-run print file.gcode
printerctl --port /dev/ttyUSB0 home
printerctl --port /dev/ttyUSB0 home X
```

Responsibilities:

- Parse global options: `--port`, `--baud`, `--timeout`, `--dry-run`, `--verbose`, `--config`.
- Reject unsafe commands unless confirmation flags are present.
- Convert validated CLI requests into application commands.
- Return meaningful exit codes.

### 6.2 `config`

Loads runtime configuration from defaults, optional config files and CLI overrides.

Initial configuration model:

```c
typedef struct {
    const char *port;
    int baud_rate;
    int timeout_ms;
    bool dry_run;
    bool verbose;
    bool apcupsd_enabled;
    bool apcupsd_auto_resume;
} printerctl_config_t;
```

Milestone 1 implements only `port`, `baud_rate`, `timeout_ms`, `dry_run`
and `verbose`. **Revised in Milestone 10:** the roadmap that originally
scheduled `apcupsd_enabled`/`apcupsd_auto_resume` for this milestone was
superseded by a new roadmap (see
[[docs/design/milestone-10-low-battery-cancellation|docs/design/milestone-10-low-battery-cancellation.md]]
§0). The new Milestone 10 adds no config keys: there is still no code
path anywhere in printerctl that reads a record or a marker back to
resume or gate anything automatically, so there is nothing an
`auto_resume` flag would need to disable, and `apcupsd_enabled` would
gate a script the operator already controls by whether they wire it into
APCUPSD at all. Both fields remain aspirational; add them only if a
future milestone gives them an actual behavior to switch.

Precedence:

1. Built-in safe defaults.
2. Configuration file.
3. CLI options.

Configuration files are loaded only through an explicit `--config PATH`.
The Milestone 1 format is root-level `key=value`, with blank lines and
full-line `#` comments allowed. Recognized keys are `port`, `baud`,
`timeout`, `dry_run` and `verbose`; unknown or duplicate keys fail. See
[[docs/design/milestone-1-cli-config]] for the complete contract.

### 6.3 `logging`

Provides structured, timestamped logs for all observable events.

Minimum events:

- Session start and end.
- Configuration summary.
- Transmitted commands.
- Received responses.
- Errors and warnings.
- Printer state changes.
- Current file and progress.
- Serial reconnect attempts.
- APCUPSD events.

**Format (resolved in Milestone 2, see
[[docs/design/milestone-2-logging]]):** plain TSV, hidden entirely behind
the `printerctl_logging` API (`include/printerctl/logging.h`,
`src/logging/logging.c`) — no call site assembles a log line itself. One
physical line per record:

```text
<RFC3339 UTC timestamp with milliseconds>\t<LEVEL>\t<event>\t<detail>\n
```

`detail` is opaque text, not a second key=value grammar; escaping
(backslash, tab, CR, LF, other control bytes and DEL as visible `\`
sequences; bytes `>= 0x80` passed through) is centralized in
`printerctl_log_record()` and is never the caller's responsibility. Levels
are `DEBUG`/`INFO`/`WARNING`/`ERROR`; `DEBUG` is filtered unless the
logger was initialized with `verbose = true`, and `ERROR` triggers an
immediate flush. The Milestone 2 event taxonomy is fixed: `session_start`,
`session_end`, `config_summary`, `command_parsed`,
`command_unavailable`, `serial_tx`, `serial_rx`, `state_transition`,
`progress`, `error`, `warning`. `logging` has no dependency on `cli` or
`config`; `cli` depends on `logging`. TSV was chosen over JSON Lines
because Milestone 2 has no real log consumer yet beyond a human reading
`stderr` — the API shape (hidden format, one narrow entry point) is what
makes a later switch to JSON Lines a `logging.c`-only change, per the
design goal already stated below.

**Privacy:** the CLI integration never logs the raw `--port` value, the
`--config` file path, `print`'s file argument, or `send`'s raw command
text — only booleans (`port_set`, `config_file_set`) and the command
name. See [[docs/design/milestone-2-logging]] §13.

Recommended initial format: line-oriented text or JSON Lines. The implementation should hide format details behind a logging API so JSON Lines can become the default without refactoring callers.

### 6.4 `serial`

Owns Linux serial communication.

Responsibilities:

- Open and close serial device.
- Configure baud rate, raw mode and timeouts.
- Read line-based responses.
- Write complete command lines with Marlin-compatible newline handling.
- Detect timeout and I/O errors.
- Avoid flooding the serial buffer.

Public API sketch:

```c
typedef struct serial_port serial_port_t;

typedef enum {
    SERIAL_OK = 0,
    SERIAL_ERR_OPEN,
    SERIAL_ERR_CONFIG,
    SERIAL_ERR_TIMEOUT,
    SERIAL_ERR_IO
} serial_status_t;

serial_status_t serial_open(serial_port_t **out, const char *path, int baud_rate, int timeout_ms);
serial_status_t serial_write_line(serial_port_t *port, const char *line);
serial_status_t serial_read_line(serial_port_t *port, char *buffer, size_t buffer_size);
void serial_close(serial_port_t *port);
```

**Resolved in Milestone 5 (see [[docs/design/milestone-5-serial]]):** the
implemented API (`include/printerctl/serial.h`) deviates deliberately
from this sketch — `printerctl_serial_port_t` is a plain stack value (no
heap, matching every other module), functions carry the `printerctl_`
prefix, every call takes an explicit error out-parameter, and close is
idempotent and returns a status. Timeouts and disconnects are distinct
explicit statuses (`ERR_TIMEOUT`, `ERR_DISCONNECTED`), and only the
standard Linux `Bxxx` baud rates are supported (Marlin's nonstandard
250000 is rejected as `ERR_UNSUPPORTED_BAUD`). Milestone 8 added
exclusive open (TIOCEXCL, released on close). Milestone 9 resolved the
deferred reconnect policy: **no automatic reconnect in the MVP** —
reopening a USB CDC device toggles DTR and resets the controller, so a
reconnected session would face a printer with all state lost, and
automatic resume is forbidden regardless; a disconnect ends the session
gracefully with an interrupted-session record. See
[[docs/design/milestone-9-recovery-records]] §6.

### 6.5 `marlin`

Parses Marlin responses and implements command acknowledgement semantics.

Recognized response classes:

- `ok`
- `Error:`
- `busy:`
- `echo:`
- `Resend:`
- temperature reports
- position reports
- firmware information
- unknown informational line

Initial behavior:

- Treat `ok` as command acknowledgement.
- Treat `Error:` as command failure.
- Treat `busy:` as non-terminal progress and continue waiting.
- Treat `echo:` as informational unless it indicates a known problem.
- Detect `Resend:` and return a clear unsupported/resend-required status for the MVP.

Future behavior:

- Add line numbering.
- Add checksums.
- Retry from requested line after `Resend:`.

**Milestone 4 resolution:** `marlin` is implemented as a pure parser
library with no serial, CLI, config, logging or G-code dependency. It
classifies one newline-stripped response line as `ACK`, `ERROR`, `BUSY`,
`ECHO`, `RESEND` or `INFO`. `ACK`, `ERROR` and `RESEND` are terminal for
the current command; `BUSY`, `ECHO` and `INFO` are non-terminal. `Resend:`
is terminal-unsupported for the MVP because line numbering/checksums are
not implemented yet. Typed parsers decode M105 temperature, M114 logical
position and M115 firmware info reports for Milestone 6 renderers.

### 6.6 `gcode`

Reads, validates and normalizes G-code files.

Responsibilities:

- Open G-code file safely.
- Stream one logical command at a time.
- Strip comments and blank lines.
- Preserve valid inline command content.
- Track source line number, sent command count and byte/file progress.
- Detect lines that exceed configured limits.
- Reject or flag disabled unsafe commands, especially `G28` unless explicitly confirmed.

**Milestone 3 resolution:** `gcode` is implemented as a streaming file
reader with no serial dependency. It accepts regular files only, snapshots
the opened file identity/size/mtime with `fstat()`, and fails if the file
changes while being read. Normalization is intentionally small:

- skip a leading UTF-8 BOM only at byte 0;
- strip full-line and inline `;` comments;
- strip parenthesized comments, including nested parentheses up to depth 8;
- trim leading/trailing spaces and tabs;
- ignore blank/comment-only lines;
- reject control bytes other than tab, oversized source lines, unmatched or
  unterminated parenthesized comments, and unexpected BOM bytes later in the
  file.

`PRINTERCTL_GCODE_LINE_MAX` is `4096` content bytes excluding the newline.
Progress is computed as floored whole-percent byte progress
(`bytes_consumed / file_size`) from the open-time file size snapshot, with
empty files treated as complete. `G28` detection is case-insensitive,
allows an optional leading `N<digits>` line word, accepts `G 28`/`G028`
forms, and blocks any `G28` suffix conservatively unless the reader is
opened with `allow_g28 = true`. The CLI dry-run print path always opens
with `allow_g28 = false`; `print` has no confirmation flag in Milestone 3.

### 6.7 `printer`

Coordinates high-level printer sessions and maps user commands to Marlin commands.

Responsibilities:

- Manage print lifecycle: idle, connecting, printing, paused, cancelling, failed, completed, interrupted.
- Coordinate G-code streaming through `gcode`, `marlin` and `serial`.
- Implement `temp`, `position`, `info`, `send`, `pause`, `resume` and `cancel`.
- Emit progress and state events.
- Stop gracefully on errors.

Initial command mapping:

| User command | Marlin command |
|---|---|
| `temp` | `M105` |
| `position` | `M114` |
| `info` | `M115` |
| `resume` | `M24` if SD-print semantics are configured; otherwise session-specific resume |
| `pause` | `M25` if SD-print semantics are configured; otherwise local streaming pause |
| `cancel` | `M524` when applicable; otherwise stop local streaming gracefully |
| `emergency-stop` | `M112`, manual explicit command only |
| `home` | `G28` (all axes); `home X`/`home Y`/`home Z` send `G28 X`/`G28 Y`/`G28 Z` (single axis). Revised 2026-07-21: min end-stops are now enabled on all three axes, so `home` needs no confirmation flag, only a configured `--port` — see [[Agents]]'s Home amendment. `G28` remains disabled everywhere else (`send`, and inside a `print` G-code file). |

### 6.8 `apcupsd`

See [[docs/apcupsd]] for the full operator-facing reference (the
triggering event, the script-to-process communication, what closes,
what is preserved, why no auto-resume, and how to inspect a cancelled
job). The summary below stays here for module-responsibility context.

Originally scoped as informational-only, because the printer itself is
not connected to the UPS and its own power is unaffected by the host's
battery level. **Revised in Milestone 10:** a low-battery signal now
also stops the host from sending further G-code, which does not depend
on the printer's power at all — it is the host's own decision to stop
cleanly before it, not the printer, may lose power. See
[[docs/design/milestone-10-low-battery-cancellation]] §0 for the full
rationale and how it reconciles with the original statement. What has
not changed, and is not weakened by this: `auto_resume` is not just
`false`, it does not exist as a code path anywhere in printerctl — there
is nothing for a config flag to gate.

On a low-battery notification (`printerctl power low-battery`, run by
`scripts/apcupsd/printerctl-low-battery.sh`):

- Deliver `SIGPWR` to the printerctl process currently streaming a
  print, found via the active-print marker (`record.h`'s
  `printerctl_record_write_active_pid()`/`_read_active_pid()`).
- That process stops sending further G-code after the current
  acknowledgement (never mid-exchange), closes the G-code file and the
  serial port, and records the session as
  `state=cancelled_power_failure` / `cause=apcupsd_low_battery` —
  timestamp, current file, last acknowledged line, progress and (as
  `unknown`, since no live query is sent) printer state, all via the
  `record` module below.
- No print running is not an error: the command is idempotent, safe to
  run whether or not a print is active, and safe to run more than once.

On power restoration: nothing happens automatically, by construction —
see §6.9. Notifying the operator of a restoration event, distinct from
the cancellation record already on disk, is deferred (see the Milestone
10 design note §7).

The software must never automatically resume a print after power
restoration, and never sends anything beyond "stop transmitting" on a
low-battery cancellation: no `M112`, no `M410`, no homing, no resume, no
additional movement (§8).

### 6.9 `record` (added in Milestone 9, extended in Milestone 10)

Write-only persistence of interrupted-session metadata, dependency-free
(`include/printerctl/record.h`, `src/record/record.c`). Any `print`
that opened its file but did not complete — failed or cancelled, by the
operator or by a power-failure signal — leaves one private, fsync'd,
never-overwritten `key=value` record (`session-<UTC timestamp>.record`)
in `$XDG_STATE_HOME/printerctl` (default
`$HOME/.local/state/printerctl`) carrying timestamp, a placeholder
`job_id` (`job-<pid>`; a real job model arrives with Milestone 13), state,
cause, the G-code file path, the serial device, commands
sent/acknowledged, last acknowledged line, byte/percent progress and
printer state (always `unknown` — never populated from a live query).
Nothing in printerctl ever reads a record back — automatic resume is
forbidden (§8 rule 6), and each record states so in its header. The
`cli` module is the Milestone 9/10 consumer.

Milestone 10 also adds a second, unrelated concern to the same module
for its shared state-directory plumbing: a live **active-print marker**
(`active-print.pid`, plain PID, silently overwritten, removed when the
stream ends) that an external notifier reads to find the right process
to signal — not an interrupted-session record, and never durable in the
way a record is (no `fsync`; see the design note §6). See
[[docs/design/milestone-9-recovery-records]] and
[[docs/design/milestone-10-low-battery-cancellation]].

### 6.10 `core` (added in Milestone 12)

Owns the application-level print lifecycle that used to live inside
`cli`'s `run_print_command()`: connect, publish the active-print
marker, stream the file, write an interrupted-session record on an
incomplete print, remove the marker, disconnect
(`include/printerctl/core/print_engine.h`, `src/core/print_engine.c`).
It reuses `printer`'s `printerctl_printer_print_file()` unchanged as
the lower-level ACK-driven streamer — Milestone 12 is an extraction,
not a rewrite; nothing in `printer`, `gcode`, `marlin` or `serial`
changed.

`printerctl_print_engine_t` knows nothing about `argv`, parsed CLI
command structs, terminal rendering, TUI, HTTP, JSON or the future Unix
socket protocol: every operator-facing message (print start, progress,
pause/resume, a power-failure cancellation notice, an active-print
marker warning, a record outcome, the terminal summary) is surfaced as
a `printerctl_print_event_t` instead of `fprintf()`, so a client adapter
decides how to present it. `cli` is the first such adapter
(`render_print_event()` in `src/cli/cli.c`, reproducing the exact
operator-facing text `print` always produced); the future daemon
(Milestone 17+) is meant to be the second, over this same engine.

Control (pause/resume/cancel/cancel-power-failure) is four
async-signal-safe setter functions
(`printerctl_print_engine_request_*()`), each a single `sig_atomic_t`
assignment — the engine never calls `sigaction()` itself; `cli` still
owns every signal installation, exactly as it did before this
milestone. See [[docs/design/milestone-12-print-engine]] and
[[docs/milestones/milestone-12]] for the full design and the as-built
deviations from it.

## 7. Runtime Flows

### 7.1 Print Flow

```text
parse CLI
load config
validate file
open log
if dry-run:
  parse and report commands without serial writes
else:
  open serial
  initialize session
  for each normalized G-code command:
    enforce safety policy
    write command
    log tx
    read responses until terminal status
    log rx
    on ok: update progress and continue
    on busy/echo: continue waiting
    on error/timeout/resend: stop gracefully and mark failed
  close serial
  write final session status
```

### 7.2 Single Command Flow

```text
parse CLI command
validate safety policy
open serial unless dry-run
send command
wait for Marlin acknowledgement or parsed response
render concise human-readable output
log full exchange
close serial
```

### 7.3 Pause, Resume and Cancel

For local host streaming, pause/resume/cancel are session controls, not only Marlin commands.

- `pause`: stop sending new G-code after the current acknowledged command; keep the serial session alive when possible.
- `resume`: continue streaming from the next unsent command in the same process/session.
- `cancel`: stop sending new commands, mark session cancelled and close cleanly.

For future daemonized or persistent operation, these commands may target an active background session. In the MVP CLI-only model, they may be implemented as direct Marlin commands or session-local controls depending on the selected execution model.

**Milestone 8 resolution:** both, through distinct mechanisms. The
streaming `print` process handles SIGUSR1 (pause after the current
acknowledgement), SIGUSR2 (resume from the next unsent command) and
SIGINT/SIGTERM (graceful cancel, exit code 9, summary still rendered);
nothing is ever sent to the printer on a host-stream pause/resume/cancel.
The `pause`/`resume`/`cancel` CLI commands send M25/M24/M524 to a print
running from the printer's SD card, with `send`-style exchange semantics.
The serial port is held in exclusive mode (TIOCEXCL) for the lifetime of
every session, so a second invocation cannot interleave bytes into an
active stream — it fails to open the device with EBUSY instead. See
[[docs/design/milestone-8-pause-resume-cancel]].

**Milestone 12 update:** the operator-facing signals are unchanged.
Internally, each handler now calls one of
`printerctl_print_engine_request_*()` on the active `core` print engine
instead of setting a CLI-local flag polled by a CLI-owned callback — see
§6.10.

### 7.4 Low-Battery Cancellation (added in Milestone 10)

```text
APCUPSD detects low battery / imminent shutdown
    v
runs scripts/apcupsd/printerctl-low-battery.sh
    v
script runs `printerctl power low-battery` (bounded by a timeout)
    v
CLI resolves the active-print marker, verifies the process is alive
    v
CLI sends SIGPWR to that process
    v
that process's SIGPWR handler calls
printerctl_print_engine_request_cancel_power_failure() on the active
print engine (checked ahead of pause/resume, per §6.10)
    v
identical graceful-stop path as an operator cancel:
  no further G-code sent, file and serial closed, session recorded
  as state=cancelled_power_failure / cause=apcupsd_low_battery
    v
process exits PRINTERCTL_EXIT_PRINT_CANCELLED_POWER_FAILURE (10)
```

No print running is not an error anywhere in this flow: `printerctl
power low-battery` is idempotent by design (§6.8), matching the later
Milestone 19 acceptance criteria for the same command once it moves onto
the Unix socket transport. See
[[docs/design/milestone-10-low-battery-cancellation]].

### 7.5 Printing Lifecycle States (Milestone 11)

The roadmap's Phase II job model names nine lifecycle states
(`queued`, `starting`, `printing`, `paused`, `completed`,
`cancelled_operator`, `cancelled_power_failure`, `failed_serial`,
`failed_printer`). This table maps each to what exists today, ahead of
Milestone 13's actual job queue:

| Roadmap state | Current reality |
|---|---|
| `queued` | Does not exist yet: a `print` invocation is not enqueued, it starts as soon as the process runs. Arrives with Milestone 13's job queue. |
| `starting` | The gap between dispatch and the first transmitted command: connecting the serial port and opening the G-code file. Not a named log state today (no `state=` transition is emitted for it specifically); implicit in the absence of a `state=printing` transition yet. |
| `printing` | `state=printing` (INFO `state_transition`), emitted once streaming begins and again after a pause resolves. |
| `paused` | `state=print_paused` (INFO `state_transition`), host streams only, entered via `SIGUSR1` and exited via `SIGUSR2` or a cancel. |
| `completed` | `PRINTERCTL_PRINT_COMPLETED`, `state=print_completed`, exit `0`. |
| `cancelled_operator` | `PRINTERCTL_PRINT_CANCELLED`, `state=print_cancelled`, exit `9`; session record `state=cancelled` / `cause=cancelled`. |
| `cancelled_power_failure` | `PRINTERCTL_PRINT_CANCELLED_POWER_FAILURE`, `state=print_cancelled_power_failure`, exit `10`; session record `state=cancelled_power_failure` / `cause=apcupsd_low_battery`. See §7.4. |
| `failed_serial` | `PRINTERCTL_PRINT_FAILED` with `status` in `{serial, timeout}`, exit `7`; session record `cause=serial` or `cause=timeout`. |
| `failed_printer` | `PRINTERCTL_PRINT_FAILED` with `status` in `{printer_error, resend, gcode, unsafe_command}`, exit `8` (`6`/`4` for a G-code file problem or an unsafe `G28`); session record's `cause` names the specific one. |

Every state past `starting` is already observable today, either as a
structured log transition or as the summary/record `state`/`cause`
fields — the roadmap's job-model states are a renaming and grouping of
what `printer.h`'s `printerctl_print_final_state_t` and
`printerctl_printer_status_t` already distinguish, not new behavior.
See `docs/safety.md` for the safety guarantees tied to each failure
state and `docs/testing.md` for how each is exercised.

## 8. Safety Rules

See [[docs/safety]] for the full operator-facing safety reference
(rationale, exit-code mapping and worked examples); the rules below are
the acceptance-criteria summary.

The following rules are mandatory acceptance criteria:

1. `G28` is disabled by default via `send` and inside a `print` G-code
   file; it is only ever available through the dedicated `home` command
   and its single-axis variants.
2. `home` (and `home X`/`home Y`/`home Z`) requires no confirmation flag
   as of 2026-07-21: min end-stops are now enabled on all three axes,
   so homing moves into a physical switch rather than crashing. See
   [[Agents]]'s Home amendment.
3. `M112` is never sent automatically.
4. No automatic homing, heating, movement or extrusion is allowed —
   `home` is still only ever an explicit, operator-requested action,
   never a side effect of anything else.
5. G-code streaming must stop gracefully on timeout, Marlin error or unsupported resend request.
6. Power restoration must not trigger automatic print resume.
7. Dry-run must never open or write to a serial device.
8. A low-battery/power-failure cancellation (Milestone 10) only ever
   stops transmitting further G-code; it never sends `M112`, `M410`,
   homing, a resume command or any additional movement automatically.

## 9. Error Handling

Use explicit status codes and structured error propagation.

Recommended categories:

- CLI usage error.
- Configuration error.
- File validation error.
- Serial open/configuration error.
- Serial timeout.
- Serial I/O error.
- Marlin command error.
- Unsupported resend request.
- Safety policy violation.
- Internal invariant failure.

No silent failures are allowed. Every failure should produce an operator-facing message and a log entry when logging is active.

Milestone 1 defines the initial process exit codes:

| Code | Meaning |
|---|---|
| `0` | Success |
| `2` | CLI usage error |
| `3` | Configuration error |
| `4` | Safety policy rejection |
| `5` | Valid request whose execution is not available yet |
| `6` | G-code file error |

## 10. Testing Architecture

Primary tests must not require printer motion.

Required layers:

1. **Unit tests**: CLI parser, config, G-code parser, Marlin parser, logging formatting.
2. **Integration tests**: serial transport through pseudo terminals and mocked Marlin server.
3. **Dry-run tests**: verify file parsing and progress without serial access.
4. **Fault tests**: timeout, malformed responses, `Error:`, `busy:`, `echo:`, `Resend:` and disconnects.
5. **Safety tests**: blocked `G28`, blocked automatic `M112`, blocked movement/heating/extrusion where applicable.
6. **Build tests**: GCC and Clang with `-Wall -Wextra -Wpedantic`.

Mock Marlin server behavior should be scriptable so tests can define response sequences per transmitted line.

See [[docs/testing]] for the concrete test binaries, what each covers,

## 13. Open Technical Decisions

These decisions should be resolved early by Codex before broad implementation:

1. ~~Whether MVP pause/resume/cancel targets only direct Marlin commands, only local streaming sessions, or both.~~ Resolved in Milestone 8: both, through distinct mechanisms. A host streaming session is controlled in-process with signals (SIGUSR1 pause, SIGUSR2 resume, SIGINT/SIGTERM graceful cancel) because the MVP has no daemon; the `pause`/`resume`/`cancel` CLI commands are direct Marlin SD-print commands (M25/M24/M524). The serial port is opened exclusively (TIOCEXCL) so the two worlds cannot collide. See [[docs/design/milestone-8-pause-resume-cancel]].
2. ~~Whether structured logs default to plain text or JSON Lines.~~ Resolved in Milestone 2: plain TSV, hidden behind the logging API. See [[docs/design/milestone-2-logging]].
3. ~~Test framework choice for C unit tests.~~ Resolved de facto by
   Milestone 11: a small hand-rolled `check(condition, description)`
   harness per test binary (no external dependency), consistent across
   all eight test binaries since Milestone 0. See [[docs/testing]].
4. ~~Maximum G-code line length and command normalization rules.~~ Resolved in Milestone 3: 4096-byte source-line limit and the normalization contract in [[docs/design/milestone-3-gcode-dry-run]].
5. ~~Whether `send` should block known unsafe commands by default.~~ Resolved in Milestone 6: `send` blocks G28 (all variants, no bypass, shared detection with the G-code reader); M112 passes through as the operator's explicit emergency stop. See [[docs/design/milestone-6-printer-commands]].
6. ~~Whether a future daemon mode is required for external pause/resume/cancel of active prints.~~ Resolved by the revised roadmap: yes. Phase II (Milestones 12-27) extracts a daemon-agnostic print engine, then builds `printerctld` around it with a Unix socket protocol; `printerctl` becomes a thin client. See `roadmap.md` and [[docs/design/unix-socket-service-analysis]] (an earlier proposal now superseded in its protocol specifics — RESP-like frames, not the key=value ones proposed there — but aligned on the daemon-owns-the-serial-port shape). **Milestone 12 done:** the daemon-agnostic print engine itself (§6.10) is extracted and `cli` is its first client adapter; the daemon process, Unix socket protocol and job queue remain future milestones (13, 17+).

Resolved decisions are recorded in milestone design notes. Configuration
path and format were resolved in [[docs/design/milestone-1-cli-config]].
Logging format and event taxonomy were resolved in
[[docs/design/milestone-2-logging]].
G-code normalization, unsafe `G28` detection and dry-run progress were
resolved in [[docs/design/milestone-3-gcode-dry-run]].
